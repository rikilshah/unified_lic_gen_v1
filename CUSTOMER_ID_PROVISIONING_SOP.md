# Blank-Card Customer ID Provisioning SOP

Status: **Documented, pending implementation**

Date agreed: 2026-07-14

## Purpose

Provision a blank card with a new 10-digit Customer ID during its first firmware flash. Because the card is blank, the value generated by the Unified Dashboard becomes the authoritative Customer ID for the card and every downstream artifact.

## Authoritative Sources

- Dashboard: [rikilshah/unified_lic_gen_v1](https://github.com/rikilshah/unified_lic_gen_v1)
- Stepper firmware: [rikilshah/stepper_control_card_v2](https://github.com/rikilshah/stepper_control_card_v2)
- Second hardware firmware: pending repository link

Local source folders are working checkouts only and must be synchronized with their GitHub repositories before implementation, building, or flashing.

## Agreed Customer ID Rules

1. Generate exactly 10 decimal digits using a random generator.
2. Leading zeroes are significant because the Customer ID is a fixed-width string, not a numeric quantity.
3. Reject any candidate containing three identical consecutive digits. Examples that are invalid include `111`, `000`, and `777` anywhere in the 10-digit value.
4. Other repeated digits are allowed.
5. Use the same generation and validation rules for both hardware models. There is no test/production difference.

## Planned Provisioning Flow

1. Start a first-provisioning session for a blank card.
2. Generate one valid Customer ID and store it in the dashboard session before modifying firmware.
3. Display the generated value for operator review.
4. Write it into the firmware header:

   ```c
   #define APP_CUST_ID_TEXT "1234567890"
   ```

5. Preserve the existing timestamped-header backup behavior.
6. Build and flash the selected hardware firmware using the existing guarded process.
7. Reconnect to the card and read the Customer ID from its identity registers.
8. Compare the read value with the generated value as an exact 10-character string.
9. Mark Customer ID provisioning successful only when the values match.
10. Use that same Customer ID for CDI JSON, key generation, manifest generation, authorization, logs, and reports.

## Final-Truth and Failure Rules

- The value generated for the blank-card session becomes final truth once flashing begins.
- Do not generate a replacement automatically after build, flash, reconnect, or validation failure.
- A mismatch fails closed and must not authorize the card.
- A retry must reuse the same stored Customer ID unless the operator explicitly abandons the uncommitted provisioning session before a successful flash.
- The persisted session format and recovery behavior will be finalized during implementation so an application restart cannot accidentally assign a different identity to a partially provisioned card.

## Implementation Gate

No dashboard code will be changed for this SOP until the second hardware firmware repository is supplied and both implementations of `customer_id_config.h` and their identity register maps have been reviewed.
